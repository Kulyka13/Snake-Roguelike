# Практична робота №10
**Тема:** Командна робота з Git та GitHub
**Результат:** GitHub-репозиторій із налаштованим командним workflow

---

### 1. Розподіл гілок (Branching Strategy)
Для безпечного тестування архітектурних змін без ризику зламати стабільну версію гри у головній гілці `main` використано окрему робочу гілку:

* `main` — основна стабільна гілка проєкту, що містить робочу збірку та актуальну документацію.
* `refactor` — експериментальна гілка для рефакторингу основного скрипту `SnakeMovement.cs` та декомпозиції його логіки на окремі модулі.

---

### 2. Робота у гілці та створення Pull Request
1. **Створення гілки та внесення змін:**
   * Через **GitHub Desktop** на основі актуальної гілки `main` створено нову гілку `refactor`.
   * У ній виконано експериментальне переписування коду `SnakeMovement.cs`: розбиття великого скрипту на менші, читабельні методи та винесення окремих механік.
   * Зміни зафіксовано комітами (`Commit`) та опубліковано на віддалений репозиторій (`Publish branch`).
2. **Створення Pull Request (PR):**
   * На GitHub відкрито **Pull Request** із гілки `refactor` у `main`.
   * В описі вказано мету рефакторингу та перелік змінених компонентів скрипту.

---

### 3. Code Review, виправлення зауважень та Merge
1. **Перевірка коду (Code Review):**
   * На вкладці **Files changed** проаналізовано різницю між старою та новою реалізацією `SnakeMovement.cs`.
   * Під час перевірки виявлено баги, що виникли після розбиття логіки (зокрема з поведінкою сегментів та таймерами).
2. **Виправлення зауважень:**
   * У гілку `refactor` додано фікси, закомічено та відправлено на сервер (`Push origin`), після чого PR автоматично оновився.
3. **Злиття гілок (Merge):**
   * Після підтвердження коректної роботи гри виконано злиття змін в основну гілку `main` через кнопку **Merge pull request**.

---

### 4. Розгляд ситуації виникнення та вирішення Merge Conflict
Під час реального злиття гілки `refactoring/snake-movement` у `main` конфліктів не виникло, оскільки зміни вносилися послідовно. Проте в межах роботи розглянуто стандартний алгоритм дій на випадок виникнення `Merge Conflict`:

1. Підтягнути актуальні зміни з цільової гілки (`main`) у робочу гілку через **Branch → Update from main** у GitHub Desktop.
2. Відкрити конфліктний файл у редакторі коду (наприклад, VS Code) та знайти ділянки, позначені маркерами `<<<<<<< HEAD`, `=======` та `>>>>>>> main`.
3. Обрати потрібний варіант коду (або об'єднати обидва), видалити службові маркери конфлікту та зберегти файл.
4. Зафіксувати вирішення новим комітом (`Commit`) і відправити зміни (`Push origin`), після чого виконати `Merge`.

---

### 5. Висновок
Відпрацьовано практичний процес роботи з гілками у Git та GitHub: створення окремої гілки для експериментального рефакторингу коду, оформлення Pull Request, перевірку та доопрацювання змін перед чистим злиттям у `main`, а також засвоєно порядок дій для вирішення потенційних конфліктів злиття (`Merge Conflict`).
